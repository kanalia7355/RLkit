# 共通srcと短い実験入口

実験を追加するときは、入力shared_sourcesにある共通APIを先に確認する。
前処理、探索手法、学習・推論、評価指標、共通I/Oはsrc/research/などの責務別モジュールに置く。
experiment.pyには引数処理、条件・パラメータ、共通関数の呼出し、結果保存を置く。
単に大きな実験ファイルを同じ内容のモジュールへ毎回コピーするのではなく、条件を引数にする。

実装応答:

```json
{
  "files": {"experiment.py": "from research.methods import compare\n..."},
  "shared_files": {"research/methods.py": "共通処理のPython全文"},
  "notes": "再利用したAPI、変更点、影響範囲、検証内容"
}
```

filesは従来どおり同一フォルダ内の.py。shared_filesは研究のsrcからの相対.pyパス。
変更しない共通処理は再送せずshared_filesを{}にする。削除はこの契約では扱わない。
srcを直接編集してから提出せず、変更案をshared_filesに返す。既存APIの変更は互換性と影響を確認する。
ファイル構文の合格は動作保証ではない。小さい入力で対象の関数が実際に使われることを確認し、
失敗した実装を後続研究で無条件に正しいものとして再利用しない。

入口からはfrom research.methods import compareのようにimportする。
ランタイムは実装時点の共通srcを実験ごとに固定し、実行用コード配下へコピーしてPYTHONPATHを設定する。
実行時に研究ルートの最新srcへsys.pathを向け直してはならない。版固定を破ってしまう。
研究ルートへの絶対パスimportや別実験ファイルからのimportも避ける。

並列作業が同じファイルを別の内容へ更新した場合は提出を拒否する。
同一内容の追加は共有できる。競合時は最新srcを確認し、独立したモジュール名に分けるなど
現在の作業票の範囲内で解消する。別Agentの変更を消して押し通さない。

インポートした過去コードはimports/sourceにある。内容・依存関係・利用条件を確認し、
必要な部分を共通APIとして整えてshared_filesへ提案する。インポートだけでsrcに昇格・実行しない。
